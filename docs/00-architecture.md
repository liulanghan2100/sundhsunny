## 二、发现的核心问题：**执行缺口**

### 问题描述

治理核**声明**规则，但**没有任何东西执行**它们。实测证据：

| 位置 | 说什么 | 有强制力吗 |
|---|---|---|
| 治理核 `depth_policy` | L2/L3 需要 owner 审批 | ❌ 只是一句话 |
| `hub.py ask` | 简报里写"需 Owner 审批" | ❌ 只是文本 |
| Codex `config.toml` | `approval_policy = "never"` | 事实上**从不询问** |

**三处结论互相矛盾**：治理核说"要审批"，Codex 说"从不问"，
而中间没有任何机制把前者变成后者。

### 这意味着什么

**一个 L3 任务被判为"需审批"，但这只是打印在屏幕上的字。**
没有任何东西阻止它被执行。

具体例子：

```
$ python hub.py ask "部署上线并转账100万"
  -> risk_level: L3
  -> status: pending_approval
  -> steps: ["本任务需 Owner 审批后才能执行（不可自行放行）"]
```

这句话**没有任何约束力**。如果我（或任何 agent）接下来直接去执行，
治理核无从阻止——因为它根本不在这条执行路径上。

### 为什么会出现这个缺口

三个模块各自设计良好，但**没有被连接**：

1. **Codex 有执行权** —— 它才是真正调用工具的地方，
   且提供了能拦截的 `PreToolUse` 钩子
2. **治理核有规则** —— 定义了什么能做什么不能做
3. **hub.py 有判断** —— 能算出任务属于 L1/L2/L3

缺的是**从 2 到 1 的通道**。

## 三、42 个模块：怎么用才对

### 两种用法，代价差 380 倍

| 方式 | 内存 | 启动 | 进程数 |
|---|---|---|---|
| 注册成 MCP 服务 | 15 × 56MB ≈ **840 MB 常驻** | 15 × 2.4s ≈ **36 秒** | 15 |
| **直接导入源码**（实测） | **单进程共享** | **2.2 秒** | 1 |

**实测数据**：42 个模块一次性全部导入，耗时约 2.2 秒，全部成功。

### 为什么直接导入就够了

每个模块的 `common.py` 里，真正干活的是那些下划线开头的内部函数，
`@mcp.tool` 装饰的只是**包了一层的壳**：

| 模块 | 内部实现（真正干活） | MCP 工具（外壳）|
|---|---|---|
| `control_plane_mcp` | `_policy_check` / `_autonomy_decision` / `_governed_cycle` | 8 个 |
| `preflight_bundle_mcp` | `_bundle` / `_classify_task` / `_search_failures` | 3 个 |
| `side_effect_admission_mcp` | `_classify_effect` / `_read_tickets` | 4 个 |
| `completion_verifier_mcp` | `_verify` | 3 个 |

**结论**：要用某模块的能力，直接 `import` 它的内部函数即可，
不需要起进程、不需要注册、不需要 stdio 握手。

```python
import sys
sys.path.insert(0, "engine/mcps")
sys.path.insert(0, "engine/memory")   # 部分模块需要
sys.path.insert(0, "core")            # 部分模块需要

import preflight_bundle_mcp.common as pf
result = pf._bundle(project="x", task="部署上线", operation="deploy", risk="L3", context={})
```

### 什么时候才该起 MCP 进程

只有当这个能力**需要给外部客户端用**（比如让 Codex 自己调用）时，
才值得起进程。包内部自己用，直接导入即可。

### 依赖注意事项

`task_queue_mcp` 依赖最多（跨 4 个包内位置），缺一个 `sys.path` 就起不来：

```
engine/mcps    -> _shared / completion_verifier / dashboard / mandatory_runtime_hook
engine/memory  -> experience_memory_mcp
core           -> Agent_OS_Core（校验、审批、锁、预算）
```

其余 14 个只需第一行。

## 四、接入 Codex 是否符合设计思想

**符合，但要说清接什么。**

### 符合的部分

Codex 的 `PreToolUse` 钩子正好是"执行权"所在：
它可以读一个动作、判断、然后**真的拦下来**（退出码 2）。

这与治理核的设计意图完全一致——治理核里那句
"校验结果不可被绕过（无后门、无 override 开关）"
只有在**有执行权的地方**才谈得上。

### 要注意的部分

接的时候必须避免两个坑：

**坑 1：别把 42 个模块全注册成 MCP。**

理由：
- 15 个常驻进程 ≈ 840 MB 内存
- 93 个工具塞进上下文，选择困难
- 其中多数（如 `dashboard_mcp`）是独立功能，与"约束执行"无关

**坑 2：别让规则变成"每次操作都弹窗"。**

`approval_policy` 现在是 `never`，说明你要的是**不被打断的工作流**。
接入后若变成"每步都问"，会比现在更糟。

## 五、接入方式

### 第一档：补上执行缺口（最值得做）

**目标**：让治理核的 L3 判定**真的能拦住动作**。

做法：写一个 Codex `PreToolUse` 钩子脚本，直接导入现有治理核：

```
Codex 要执行某工具
    ↓
PreToolUse 钩子被调用（传入 tool_name / tool_input）
    ↓
1. 查宪法层：这个路径受保护吗？      -> validator.validate_write
2. 查风险分级：这个动作是 L3 吗？    -> risk_classifier
3. 判断：
   - 命中宪法保护 -> 拦截（exit 2，说明原因）
   - L3 且无有效审批 -> 拦截（提示需审批）
   - 其余 -> 放行
    ↓
Codex 按钩子结论执行或中止
```

**为什么用直接导入**：钩子每次都要判断，如果走 MCP 进程，
每次都要付进程启动开销（2.4 秒）。直接导入治理核是 **0.01 秒**（实测）。

**代价**：一个脚本（约 100 行），复用现有治理核，零新增依赖。

**收益**：治理核从"纸上规则"变成"真的拦得住"。

### 第二档：需要哪个能力就导入哪个

**不要注册 MCP 进程。** 直接导入源码即可（见第三节的实测对比）。

比如要用执行前检查：

```python
import sys
sys.path.insert(0, "engine/mcps")
import preflight_bundle_mcp.common as pf

# _bundle 才是真正干活的，MCP 工具只是包了层壳
result = pf._bundle(project="x", task="部署上线",
                    operation="deploy", risk="L3", context={})
```

**几个值得优先想到的**：

| 模块 | 内部入口 | 补什么缺口 |
|---|---|---|
| `preflight_bundle_mcp` | `_bundle` | 执行前统一检查 |
| `control_plane_mcp` | `_policy_check` / `_autonomy_decision` | 策略检查、自主权决策 |
| `side_effect_admission_mcp` | `_classify_effect` | 副作用分级 |
| `completion_verifier_mcp` | `_verify` | 按证据验证完成度 |

**代价**：导入即用，无进程开销。

### 第三档：其余模块按需取用

`dashboard_mcp` / `failure_replay_mcp` / `memory_consolidation_mcp` 等
是独立的增值功能，需要时直接导入调用即可。

`hub.py mcps` 可查清单，`docs/02-capabilities.md` 有用途说明。

## 六、明确不建议做的事

| 事项 | 为什么不做 |
|---|---|
| 把 42 个模块注册成 MCP 服务 | 约 2.3GB 常驻 + 100 秒启动，而直接导入只要 2.2 秒 |
| 重命名 `skills-shared-candidate` | 牵动 5 处引用，收益只是好看 |
| 把 `recovery/` 接进主流程 | hub 不执行高风险动作，无失败可恢复（详见审计报告第十节）|
| 追求"所有模块都接通" | 各模块本就是可独立取用的部件，不必全连通 |

---

## 七、一句话总结

**这个包的结构是好的，缺的不是"更多能力"，而是"把已有的能力接通"。**

治理核能算、Codex 能拦，中间那条线没接。
这是当前最值得注意的一处结构性缺口。
